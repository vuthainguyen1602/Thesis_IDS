\begin{abstract}
Deploying machine learning (ML) based intrusion detection on resource-constrained edge devices requires balancing accuracy, latency, and operational cost. We present a split-deployment IDS architecture across two NVIDIA Jetson Orin Nano Super devices connected through Apache Kafka~\cite{kreps2011kafka}. The system implements a two-stage pipeline: (1) a lightweight autoencoder anomaly gate on Jetson~\#1 filters benign traffic, and (2) a PySpark \texttt{PipelineModel} classifier on Jetson~\#2 processes only suspicious flows. Central infrastructure (Kafka, PostgreSQL, InfluxDB, Grafana) runs on a host PC. The classifier is the model selected by our companion Spark ML study under a \emph{leakage-aware} evaluation (label-leaking port features removed, feature-level duplicate flows eliminated). We evaluate three distributed modes (pipeline split, horizontal Kafka consumer scaling, and a Spark standalone cluster) while streaming CICIDS2017 network flows~\cite{sharafaldin2018toward}. We report throughput, latency, and the gate's recall--skip trade-off across the three deployment modes; quantitative results, including p95 batch latency on Jetson Orin Nano Super under streaming load, are filled in after benchmarking.

\keywords{Intrusion detection \and Edge computing \and Jetson Orin Nano Super \and Kafka \and PySpark \and Stream processing.}
\end{abstract}

\section{Introduction}

Network intrusion detection systems (IDS) increasingly must operate closer to data sources to reduce bandwidth and response time~\cite{shi2016edge}. Edge devices such as the NVIDIA Jetson Orin Nano Super offer limited CPU, memory, and thermal headroom, making monolithic ML inference challenging. A practical edge IDS must therefore decide \emph{which} model to deploy---one that is small, accurate, and explainable---and \emph{how} to distribute inference across nodes under streaming load.

\textbf{Contributions.}
(1) A two-stage distributed IDS combining a lightweight anomaly gate with a Spark-based classifier;
(2) Three deployment modes for a two-node Jetson cluster (pipeline split, horizontal scaling, Spark standalone cluster);
(3) An end-to-end performance evaluation reporting throughput, latency percentiles, and per-node resource usage, which are metrics that offline studies typically omit;
(4) Open, reproducible scripts integrated with a \emph{leakage-aware} Spark ML training pipeline, so the deployed model is the one validated under a rigorous offline protocol.

\section{Related Work}

Edge computing pushes analytics closer to data sources to reduce latency and bandwidth~\cite{shi2016edge,hamdan2020edge}. Prior edge IDS studies~\cite{sforzin2016rpids,baalaji2025ensemble,asghar2026hedid} benchmark single-node inference on resource-constrained boards, including recent NVIDIA Jetson deployments, but they rarely evaluate multi-node Kafka pipelines with explicit role separation. Streaming platforms such as Kafka~\cite{kreps2011kafka} decouple producers and consumers; however, most ML-based IDS papers~\cite{khraisat2019survey,ferrag2020deep,vinayakumar2019deep} report offline batch accuracy without end-to-end throughput or per-node resource traces.

\textbf{Split inference.} Anomaly-detection surveys~\cite{chandola2009anomaly,ruff2021unifying} motivate two-stage designs: a lightweight gate followed by a heavier classifier. Autoencoder-based detectors~\cite{lopez2017autoencoder,hasan2025iiot} and federated edge IDS~\cite{nguyen2019diot} explore similar ideas on servers or homogeneous edge nodes, and recently on a single Jetson Nano~\cite{hasan2025iiot}, but none use PySpark MLlib classifiers on the NVIDIA Jetson Orin Nano Super~\cite{nvidia2019jetson}. Our companion ML study selects a leak-free SHAP Top-30 model on CICIDS2017~\cite{sharafaldin2018toward,lundberg2017unified}; this paper focuses on \emph{how} to deploy that model across two Jetsons with a measurable gate-skip ratio and three scaling modes. Table~\ref{tab:related-work} positions our system against representative related work.

\section{System Architecture}

\subsection{Split Deployment Overview}

Figure~\ref{fig:architecture} shows the split-deployment architecture. A host PC runs Kafka, PostgreSQL, InfluxDB, and Grafana. Two Jetson Orin Nano Super nodes consume network-flow messages from topic \texttt{ids-network-flow}. In pipeline-split mode, Jetson~\#1 runs the anomaly gate and forwards only \emph{suspicious} flows to topic \texttt{ids-suspicious-flow}. Jetson~\#2 then applies the PySpark classifier and writes the classification results back to PostgreSQL. Both nodes stream performance metrics to InfluxDB/Grafana and raise alerts via Email/Slack (dashed arrows in Fig.~\ref{fig:architecture}).

\subsection{Pipeline Roles}

\begin{itemize}
  \item \textbf{anomaly\_gate:} sklearn autoencoder + scaler; the MSE threshold is calibrated offline (Exp~8) as a quantile of a held-out \emph{benign validation split} (10\% of benign training flows, never the test set), so the operating point is committed before evaluation.
  \item \textbf{classifier:} PySpark \texttt{PipelineModel} with the leak-free SHAP-selected feature set.
  \item \textbf{full:} combined pipeline for horizontal scaling via Kafka consumer groups.
\end{itemize}

\subsection{Monitoring and Alerting}

Each node tags metrics with \texttt{EDGE\_NODE\_ID} in InfluxDB and PostgreSQL. Alerts are emitted from a designated primary node only, avoiding duplicate notifications.

\section{Implementation}

Training and model export run on a Spark standalone cluster (host PC as master, two Jetson Orin Nano Super devices as workers) using Apache Spark ML~\cite{zaharia2010spark}; the cluster topology is shown in Fig.~\ref{fig:spark-cluster}. The host only coordinates (Spark master) and does \emph{not} run an executor, so all reported training compute reflects the two homogeneous Jetson workers rather than the stronger host CPU. The edge stack is implemented in Python (\texttt{jetson/edge/}) with configurable roles via environment variables. Every offline run logs its configuration (random seed, leakage/dedup switches, library versions) so each exported model is traceable to the exact pipeline that produced it.

\label{sec:bridge}

This paper does \emph{not} compare Spark against Jetson Orin Nano Super as competing platforms. The two components address complementary phases of the same train--deploy pipeline (Fig.~\ref{fig:train-deploy}). Spark answers \emph{which model and how many features} achieve acceptable accuracy on the full CICIDS2017 dataset~\cite{sharafaldin2018toward}, whereas the Jetson Orin Nano Super answers \emph{whether that model can run in real time} under memory, thermal, and bandwidth constraints at the network edge~\cite{shi2016edge}.

\subsection{Offline Phase (Spark ML), Leakage-Aware}

In our companion ML study, we evaluate four feature configurations---baseline (all features), RF Importance Top-30, SHAP Top-30, and PCA ($k$=40)---under a fixed 80/20 train--test split, using eight Spark ML classifiers and statistical validation (repeated paired resampling and permutation tests). PCA uses $k$=40 rather than 30 because it \emph{extracts} components (linear combinations spreading variance across many axes) rather than \emph{selecting} original features, so it needs more components to retain comparable variance; across the common $\{20,30,40\}$ sweep, $k$=40 retains the most variance and is the fairest representative operating point for PCA. LightGBM is excluded because its SynapseML native libraries are x86\_64-only and cannot run on the ARM64 Jetson Orin Nano Super deployment target. Crucially, the offline protocol is \emph{leakage-aware}: it removes information that would be unavailable at deployment time but that otherwise inflates test scores. Motivated by documented labelling and duplication errors in CICIDS2017~\cite{lanvin2023errors}, the label-leaking \texttt{destination\_port} feature is removed and flows that are identical on all feature columns are de-duplicated before splitting. This yields realistic F1 values (Table~\ref{tab:spark-edge-bridge}) rather than the near-perfect scores obtained when these leaks are left in place. Offline metrics constrain \emph{which} exported model is worth deploying; they are not directly comparable to edge throughput or latency.

\subsection{Edge Phase (Jetson Orin Nano Super)}

The exported \texttt{PipelineModel} (VectorAssembler $\rightarrow$ StandardScaler $\rightarrow$ classifier) is loaded on Jetson~\#2 with only the selected SHAP features, reducing assembly and inference cost relative to the $\approx$78-feature baseline. A lightweight sklearn autoencoder gate (Exp~8) on Jetson~\#1 filters benign flows before they reach Spark inference, further lowering load on the classifier node. End-to-end edge evaluation measures throughput (flows/s), latency p50/p95 (ms), per-node CPU/RAM/temperature, attack-class F1, and gate-skip ratio, none of which the offline Spark experiments capture.

\section{Results}
\label{sec:benchmark-results}

We run \texttt{run\_benchmarks.sh} on the Jetson hardware in three phases (\texttt{local}, \texttt{run}, \texttt{merge}). Each configuration is measured over five repetitions preceded by representative warmup traffic (excluded from the measured window, so JVM/JIT warmup does not inflate early-batch latency); Table~\ref{tab:benchmark} reports mean~$\pm$~std across repetitions. All metric queries are aligned to the exact load window rather than a trailing time range. Latency percentiles are computed per node over the raw per-flow samples logged during the window, and pipeline throughput is counted as \emph{final verdicts per second} (a flow's verdict is issued either at the gate, for skipped flows, or at the classifier), which avoids double-counting forwarded flows in pipeline-split mode. Results are exported to \texttt{summary.csv} and filled into Table~\ref{tab:benchmark}, with throughput and p95 latency across modes visualized in Fig.~\ref{fig:edge-modes}.

\textbf{Energy efficiency.} On-board power is sampled with \texttt{tegrastats} during each run; the average rail power is integrated over the window and the idle baseline subtracted to obtain the active energy, divided by the number of classified flows to report energy-per-inference (mJ). For pipeline-split mode this sums the active energy of both nodes (gate on Jetson~\#1, classifier on Jetson~\#2). If the anomaly gate offloads a \ph{gsA}\% fraction of benign traffic before the heavier Spark classifier runs, the pipeline-split mode is expected to lower energy-per-inference relative to the single-node baseline; however, the added node and extra Kafka hop introduce overhead that may offset this saving, so Table~\ref{tab:benchmark} quantifies whether the net effect holds.

\subsection{Inference-engine baseline (cost of the unified stack)}
\label{sec:engine-baseline}

We deploy a Spark \texttt{PipelineModel} on the edge for \emph{consistency with the distributed training phase} --- the same stack trains on the cluster and serves on the device. To quantify the price of that unification, we benchmark the \emph{same} RandomForest (matched hyper-parameters) on the \emph{same} SHAP Top-30 features through lighter single-node engines: scikit-learn (CPU, no JVM) and ONNX Runtime (Table~\ref{tab:engines}). Accuracy is comparable by construction; the comparison targets inference cost. We expect the JVM/Spark stack to incur higher latency and memory than sklearn/ONNX on an 8\,GB ARM board; reporting this honestly motivates an export path (\texttt{PipelineModel}~$\rightarrow$~ONNX/TensorRT) for inference while retaining Spark for training, which we leave as future work.

The anomaly gate is a \emph{tunable} filter rather than a single point: sweeping its threshold trades attack recall against the fraction of benign flows offloaded from Spark (Fig.~\ref{fig:gate}). This lets an operator pick an operating point that fits the available edge budget.

\section{Discussion}

Pipeline split relieves Spark of most benign traffic, and the realized benefit scales with the gate-skip ratio (\ph{gsA}\% in our runs). Horizontal scaling improves throughput when Kafka partitions $\geq 2$. Spark standalone cluster mode adds coordination overhead on the Orin Nano Super and is most useful when model or batch size exceeds single-node memory.

As summarized in Sec.~\ref{sec:bridge}, offline Spark experiments and edge Jetson benchmarks answer different questions. Feature reduction from $\approx$78 to 30 dimensions (SHAP Top-30) directly reduces \texttt{VectorAssembler} and \texttt{PipelineModel} cost on the Orin Nano Super, while the anomaly gate skips a large fraction of benign flows before Spark inference is invoked. Together, these design choices connect the accuracy-oriented conclusions of the companion ML study to a deployable, measurable edge architecture.

\subsection{Limitations}

Benchmarks are obtained on a two-node lab cluster over Wi-Fi; wired networking and larger clusters may shift latency tails. The anomaly-gate threshold trades attack recall against the gate-skip ratio, so we characterize it as an operating curve (Fig.~\ref{fig:gate}) rather than a single point and leave live-traffic re-calibration of the gate to future work. Each configuration is repeated five times with warmup traffic excluded from the measured window (Sec.~\ref{sec:benchmark-results}); nevertheless, run-to-run variance on a thermally constrained board can remain non-trivial and is reported alongside the means. Latency percentiles are computed on each node from its raw per-flow samples, and the cluster-level p95 is reported conservatively as the \emph{worst node's} p95 (never a percentile of per-host means); besides on-node inference latency (preprocess+predict), end-to-end latency (producer send $\rightarrow$ verdict) is measured from producer timestamps, but its absolute values are meaningful only when all hosts share an NTP-synchronized clock, and DB-write cost is excluded. Running PySpark on the JVM on an 8\,GB Jetson incurs substantial overhead; Spark is chosen for consistency with the distributed training phase rather than to optimize single-node inference --- the overhead is quantified by the single-node sklearn/ONNX baseline in Sec.~\ref{sec:engine-baseline}, and TensorRT acceleration remains future work --- and the GPU ($\sim$67 TOPS) is not yet exploited by the CPU-only pipeline. The energy-per-inference (mJ) figures subtract a single idle baseline measured once before each run (Sec.~\ref{sec:benchmark-results}), so drift in background power (e.g., thermal effects) within a run is not captured; in pipeline-split mode they sum the active energy of both nodes, and the gate-skip saving does not subtract the cost of the autoencoder that runs on 100\% of flows. Finally, our results are tied to CICIDS2017 replay, so validation on live traffic remains future work, and the system has not been evaluated against traffic deliberately crafted to evade detection (adversarial evasion).

\section{Conclusion}

We presented a reproducible distributed edge IDS for Jetson Orin Nano Super clusters with Kafka streaming and PySpark inference, deploying a model validated under a leakage-aware offline protocol. Future work includes TensorRT optimization, live-traffic validation, and federated retraining under drift.
